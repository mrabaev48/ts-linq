# Computed Columns (Generated Columns)

This guide explains how to define, use, migrate, and reason about computed (generated) columns across supported SQL dialects.

## What is a computed column?

A computed column is a database column whose value is produced by an expression evaluated by the database engine. It is inherently read-only from the ORM perspective.

Examples:
- total_with_vat = amount * 1.2
- full_name = first_name || ' ' || last_name

## ORM rules and constraints

- Read-only: computed columns are excluded from INSERT and UPDATE. Attempting to set or update them raises ValidationError.
- No conflicts allowed with:
  - defaultValue
  - defaultExpression
  - isGenerated (identity/auto-increment)
  - isVersion (optimistic concurrency token)
- Migrations: changing a computed column is rendered as drop+add (baseline for cross-dialect safety). SQLite may require table rebuild to drop columns.

## Dialect support and storage modes

- PostgreSQL: STORED only (`GENERATED ALWAYS AS (...) STORED`).
- MySQL ≥ 5.7: `VIRTUAL` and `STORED` are supported.
- SQLite ≥ 3.31: `VIRTUAL` and `STORED` (project defaults to `VIRTUAL`; older versions require fallback/skip in tests).
- MSSQL: `AS (...)` with optional `PERSISTED`.

## Defining computed columns

With decorators (Stage-3):

```ts
@Entity()
class Order {
  @PrimaryKey() id!: number;
  @Column() amount!: number;
  // Mark as computed via a Stage-3 decorator or metadata registration
  // @ComputedColumn(() => 'amount * 1.2')  // example if decorator is used
  totalWithVat!: number;
}
```

Programmatically (metadata):

```ts
MetadataStorage.addEntity(Order, 'orders');
MetadataStorage.addColumn(Order, {
  propertyName: 'totalWithVat',
  columnName: 'total_with_vat',
  type: 'INTEGER',
  nullable: true,
  isComputed: true,
  computedExpression: 'amount * 1.2'
});
MetadataStorage.addPrimaryKey(Order, 'id');
```

Optionally specify storage mode (where available):

```ts
MetadataStorage.addColumn(Product, {
  propertyName: 'priceWithVat',
  columnName: 'price_with_vat',
  type: 'INTEGER',
  nullable: true,
  isComputed: true,
  computedExpression: 'price * 1.2',
  // One of: 'VIRTUAL' | 'STORED' | 'PERSISTED' (dialect-dependent)
  // MySQL: VIRTUAL/STORED, SQLite: VIRTUAL/STORED, MSSQL: PERSISTED, Postgres: STORED
  // @ts-expect-error: property is optional and dialect-specific
  computedStorage: 'STORED'
});
```

## Migrations

- CREATE TABLE renders the computed expression with appropriate keywords per dialect.
- ADD COLUMN for computed fields is supported; ALTER is implemented as drop+add for cross-dialect safety.
- DROP COLUMN for SQLite requires table rebuild (not generated by minimal diff strategy).

## Testing and feature detection

- Integration tests are provided for PostgreSQL, MySQL, MSSQL, and SQLite.
- SQLite tests include runtime feature detection and skip when the environment version < 3.31.

## When to use computed vs defaultExpression

- Use `defaultExpression` for values set once at insert time (e.g., `CURRENT_TIMESTAMP`). Field remains writable.
- Use computed columns for values derived from other columns that must always remain consistent and non-editable by the app.

## Caveats

- Expression portability varies between dialects (string concatenation, JSON ops, etc.). Keep expressions simple or dialect-specific when necessary.
- Indexing computed expressions may require functional indexes and dialect-specific DDL.
