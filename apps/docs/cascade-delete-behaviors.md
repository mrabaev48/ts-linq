# Cascade Delete Behaviors

`onDelete()` configures what happens to dependent rows — both at the **database level** (FK constraint clause) and **client-side** (ChangeTracker pre-pass) — when a principal entity is deleted.

Seven behaviors mirror EF Core's `DeleteBehavior` enum exactly.

## EF Core parity

```typescript
// EF Core C# original:
// modelBuilder.Entity<Post>()
//   .HasOne(p => p.Blog)
//   .WithMany(b => b.Posts)
//   .OnDelete(DeleteBehavior.Cascade);

// ts-linq equivalent:
mb.entity(Post)
  .hasOne((p) => p.blog)
  .withMany((b) => b.posts)
  .hasForeignKey((p) => p.blogId)
  .onDelete(DeleteBehavior.Cascade);
```

## Behavior matrix

| `DeleteBehavior` | DB `ON DELETE` clause | Client-side ChangeTracker action |
|---|---|---|
| `Cascade` | `CASCADE` | Marks tracked dependents `Deleted`; recurses through the graph |
| `Restrict` | `RESTRICT` | None — DB raises an error if dependents exist |
| `SetNull` | `SET NULL` | Sets FK column to `null` on tracked dependents; marks them `Modified` |
| `ClientSetNull` | _(no clause)_ | Sets FK column to `null` on tracked dependents; marks them `Modified` |
| `NoAction` | `NO ACTION` | None — DB raises an error if dependents exist (deferred check) |
| `ClientCascade` | _(no clause)_ | Marks tracked dependents `Deleted`; recurses through the graph |
| `ClientNoAction` | _(no clause)_ | None |

`Client*` variants omit the database-level clause — the cascade or null-set logic runs only inside the ChangeTracker before any SQL is sent to the database. The database FK constraint itself uses its default action (`NO ACTION`).

## Fluent API

`onDelete()` is available on all relationship builder types:

```typescript
import { DeleteBehavior } from '@ts-linq/types';

class AppDbContext extends DbContext {
  protected onModelCreating(mb: ModelBuilder): void {
    // One-to-many: DB CASCADE — database deletes Comment rows automatically
    mb.entity(Comment)
      .hasOne((c) => c.post)
      .withMany((p) => p.comments)
      .hasForeignKey((c) => c.postId)
      .onDelete(DeleteBehavior.Cascade);

    // One-to-many: DB SET NULL — FK column is nulled when parent is deleted
    mb.entity(Post)
      .hasOne((p) => p.author)
      .withMany((a) => a.posts)
      .hasForeignKey((p) => p.authorId)
      .onDelete(DeleteBehavior.SetNull);

    // One-to-one: RESTRICT — deletion is forbidden while child exists
    mb.entity(User)
      .hasOne((u) => u.profile)
      .withOne((p) => p.user)
      .hasForeignKey<Profile>((p) => p.userId)
      .onDelete(DeleteBehavior.Restrict);

    // Client-side only: ChangeTracker nulls FK before save; DB sees no ON DELETE clause
    mb.entity(Post)
      .hasOne((p) => p.category)
      .withMany()
      .hasForeignKey((p) => p.categoryId)
      .onDelete(DeleteBehavior.ClientSetNull);
  }
}
```

## Client-side cascade walk

When `saveChanges()` is called, the ChangeTracker runs a **cascade pre-pass** (`CascadeWalker`) before writing any SQL:

1. Collect all entities currently in `Deleted` state.
2. For each deleted principal, scan every other tracked entity whose FK column points to it.
3. Apply the configured behavior:
   - `Cascade` / `ClientCascade` → mark the dependent `Deleted`, then recurse into its own dependents.
   - `SetNull` / `ClientSetNull` → set the FK column to `null` and transition the dependent to `Modified`.
   - All other behaviors → leave the dependent unchanged (the database constraint takes over).

**Cycle detection**: a visit-key set prevents infinite loops on self-referencing FK graphs (e.g. `Employee.managerId → Employee`).

**Scope**: only entities currently loaded into the ChangeTracker are affected. Rows in the database that are not tracked are handled entirely by the database-level constraint.

```typescript
// Both blog (Deleted) and post (FK to blog) are tracked.
// With Cascade, post is automatically marked Deleted by the CascadeWalker.
ctx.changeTracker.remove(blog, Blog);
await ctx.saveChanges();
// → DELETE FROM posts WHERE id = 10
// → DELETE FROM blogs WHERE id = 1
```

## DDL output

The `ON DELETE` clause appears in the `CREATE TABLE` DDL generated by migrations:

### PostgreSQL

```sql
CREATE TABLE IF NOT EXISTS "posts" (
  "id" INTEGER,
  "blogId" INTEGER,
  PRIMARY KEY ("id"),
  FOREIGN KEY ("blogId") REFERENCES "blogs" ("id") ON DELETE CASCADE
)
```

### MySQL

```sql
CREATE TABLE IF NOT EXISTS `posts` (
  `id` INTEGER,
  `blogId` INTEGER,
  PRIMARY KEY (`id`),
  FOREIGN KEY (`blogId`) REFERENCES `blogs` (`id`) ON DELETE CASCADE
)
```

### SQL Server

```sql
IF OBJECT_ID(N'posts', N'U') IS NULL BEGIN
  CREATE TABLE [posts] (
    [id] INTEGER,
    [blogId] INTEGER,
    PRIMARY KEY ([id]),
    FOREIGN KEY ([blogId]) REFERENCES [blogs] ([id]) ON DELETE CASCADE
  )
END
```

`Client*` behaviors emit no `ON DELETE` clause — the database uses its default (`NO ACTION`).

## Defaults

EF Core defaults:
- Required relationships (`nullable: false`) → `ClientCascade`
- Optional relationships (`nullable: true`) → `ClientSetNull`

`ts-linq` does not auto-assign defaults — `onDelete()` must be called explicitly to set a non-default behavior.
