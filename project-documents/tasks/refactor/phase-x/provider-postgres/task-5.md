# Refactor: Move Postgres `ON CONFLICT` upsert SQL into the dialect

## Problem
`PostgresProvider.upsert` hand-builds the `INSERT ... ON CONFLICT (...) DO UPDATE SET ... RETURNING *`
statement by string concatenation in the provider, duplicating column-classification that the
dialect already owns. (Identifiers are double-quoted here, which is safer than the MSSQL/MySQL
copies, but the SQL still lives in the wrong layer.)

## Evidence
- `packages/provider-postgres/src/PostgresProvider.ts:258-291` — `upsert`.
- `:266-287` builds `insertCols`/`names`/`placeholders`/`conflictTargets`/`setClause` and the final SQL at `:287`.
- Column-classification logic (`!isComputed`, `!isGenerated`, PK handling) overlaps the dialect's insert/update builders.

## Why this is bad
- SQL generation belongs in `@ts-linq/dialect-postgres` (separation of concerns).
- Duplicated column-classification drifts from the dialect's insert/update.

## Target architecture
Add `buildUpsert(entity, metadata)` to the Postgres dialect (Builder), reusing its identifier
quoting + column helpers; provider calls it, coerces params via the shared coercer (task-2), and
executes. Guard with `supportsUpsert` capability (task-4).

## Proposed refactor
1. Implement `buildUpsert` in dialect-postgres (`ON CONFLICT ... DO UPDATE ... RETURNING *`).
2. Replace the provider body with a dialect call + coerced params + execute.

## Suggested design patterns
- **Builder**, **Template Method/Strategy** (per-dialect upsert syntax).

## Testing plan
- Unit (dialect): snapshot generated SQL incl. quoted identifiers + reserved-word column.
- Provider: upsert round-trip via the contract suite (task-6).

## Acceptance criteria
- [ ] No raw upsert SQL concatenation in `PostgresProvider`.
- [ ] Upsert SQL generated by the dialect.
- [ ] Upsert params go through the shared coercer.
- [ ] Dialect snapshot tests cover the upsert SQL.
