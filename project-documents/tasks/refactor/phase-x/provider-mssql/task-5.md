# Refactor: Move hand-assembled `MERGE` upsert SQL out of the provider into an MSSQL upsert writer/dialect

## Problem
`MssqlProvider.upsert` builds a raw `MERGE` statement by string concatenation directly inside the
provider, duplicating column-filtering logic that the dialect already owns for insert/update.
This places SQL-generation responsibility in the wrong layer and risks identifier-quoting bugs.

## Evidence
- `packages/provider-mssql/src/MssqlProvider.ts:285-323` — `upsert` computes `updatable`,
  `sourceCols`, `insertableCols`, builds `sourceSelect`/`onClause`/`setClause`/`insertCols`/`insertVals`
  and concatenates the final `MERGE ... USING (SELECT ...) ON (...) WHEN MATCHED ... WHEN NOT MATCHED ...;`.
- Column names are interpolated **unquoted** (`${c.columnName}` at `:303-312`) unlike the
  dialect's quoted paths, so a column named with a reserved word or special char breaks here only.
- Parallel duplication: `MySqlProvider.upsert` `:224-246` and `PostgresProvider.upsert` `:258-291`
  each hand-build their own dialect-specific upsert SQL in the provider too.

## Why this is bad
- Separation-of-concerns violation: SQL generation belongs in `@ts-linq/dialect-mssql`, not the provider.
- Inconsistent quoting between the provider's MERGE and the dialect's insert/update is a latent injection/breakage risk for non-trivial identifiers.
- Three providers reimplement upsert assembly, none reusing the dialect's column-filter helpers.

## Target architecture
Push upsert SQL generation down to the dialect layer (Clean Architecture: provider orchestrates,
dialect generates SQL). Add `buildUpsert(entity, metadata)` to each dialect (mirroring
`buildInsert`/`buildUpdate`), or an `MssqlMergeWriter` collaborator that reuses the dialect's
identifier-quoting and column-classification helpers. The provider then calls one method and
executes the result. SOLID: SRP (provider stops generating SQL), DRY (shared column filtering),
OCP (dialect owns syntax variation).

## Proposed refactor
1. Add `buildUpsert` to the MSSQL dialect using its existing `quoteIdentifier` + column helpers.
2. Replace `MssqlProvider.upsert`'s body with a call to `dialect.buildUpsert` + execute.
3. Apply the same in MySQL/PG (`task-5` of each) so all upserts live in dialects.
4. Add a capability flag (`supportsMerge`, see `task-4.md`) consulted before calling.

## Suggested design patterns
- **Builder** — dialect builds the statement; provider executes it.
- **Template Method / Strategy** — per-dialect upsert syntax behind a uniform `buildUpsert`.

## Testing plan
- Unit (dialect, no driver): snapshot the generated `MERGE`/`ON CONFLICT`/`ON DUPLICATE KEY` SQL, including quoted identifiers and the reserved-word column case.
- Provider: upsert round-trip via the contract suite (`task-6.md`).
- Regression: existing upsert behavior preserved (PK present vs absent → insert fallback at `:288`).

## Acceptance criteria
- [ ] `MssqlProvider.upsert` contains no raw SQL string concatenation.
- [ ] Upsert SQL is generated by the dialect with proper identifier quoting.
- [ ] A reserved-word / special-char column name is quoted correctly in the generated SQL.
- [ ] MySQL/PG upserts likewise move into their dialects (their `task-5`).
- [ ] Dialect-level snapshot tests cover the generated upsert SQL.
